Chapter 4: System Demonstration

This chapter presents the operational walkthrough of the Kirby's Hardware POS and Inventory Management System as implemented in the web application. The demonstration follows the actual navigation labels, forms, buttons, data views, Firebase-backed workflows, offline indicators, and Kirby assistant behavior. Screenshot boxes are provided as placeholders for the student's captured application screenshots; mobile and tablet views should be included where the interface materially differs.

The application opens with a Firebase Authentication login screen. After authentication, the user is taken to a role-aware dashboard containing the Overview, Point of Sale, Inventory, Orders, Customers, Reports, Audit Trail, User Management, and Settings pages. The Administrator can access administrative pages, while the Cashier is limited to operational pages required for sales and customer service.

4.1 User Login/Authentication

The authentication module is the entry point to the entire system. It enforces identity verification through Firebase Authentication and role-based access control through the store's Firestore profile collection. The demonstration covers the login screen, the Administrator-controlled cashier password-reset workflow, and the two distinct post-authentication experiences for the Administrator and Cashier roles.

4.1.1 Login Screen

Figure 4.1 — Login Screen

The login screen appears when the application is opened without an active Firebase session. It is a two-panel layout: the left panel displays the Kirby's Hardware branding and system status, while the right panel contains the authentication form.

The form captures two fields — email address and password — and includes a show-password toggle, a "Remember me" checkbox, and guidance that cashier password resets must be requested from an Administrator. Inline validation prevents submission when the email is malformed or the password is shorter than six characters.

Step-by-Step Login Workflow

  1. Open the application URL in a browser. The login screen renders.
  2. Enter a registered email address in the Email Address field. The system validates that the value is a well-formed email; if not, an inline error appears below the field.
  3. Enter the account password in the Password field. The show-password toggle can be used to verify the input visually.
  4. Click Sign In. The button switches to a spinner state while the request is in flight.
  5. Firebase Authentication validates the credentials and issues a signed ID token.
  6. The client fetches the user's profiles/{uid} document from Firestore to determine the role (admin or cashier) and the active flag.
  7. If the account is active, the dashboard loads with role-appropriate navigation. If the account has been deactivated, the system signs the user out and displays an error toast.

Failed Login Behavior

Three distinct failure modes are handled with separate messages, and provider error text is never shown to the user:

Failure Mode Behavior
Invalid credentialsToast: "Unable to sign in." The password field is cleared and focus returns to it.
Deactivated accountToast: "This account has been deactivated. Contact an administrator." The user is signed out immediately.
Network failureToast: "Unable to sign in." No technical detail is leaked.

4.1.2 Forgot Password Flow

Figure 4.2 — Administrator Password-Reset Action

Cashier accounts do not use a public self-service password-reset link. A cashier must request a reset from an Administrator. This keeps account recovery under store management and prevents a cashier from initiating a reset for another account from the login screen.

Step-by-Step: Administrator Reset for a Cashier

  1. The Administrator signs in using the administrator account.
  2. Open User Management from the dashboard sidebar.
  3. Locate the cashier account in the user list. The table identifies the account by name, email, role, and active status.
  4. Click the key icon in the account's action controls. The action is labeled Send password reset.
  5. Confirm the reset request when prompted. The system sends a Firebase password-reset email to the cashier's registered email address.
  6. The cashier opens the email, follows the reset link, creates a new password, and signs in again from the login screen.

Password Reset Outcomes

Condition Observed application behavior
Administrator confirms resetA Firebase password-reset email is sent to the selected cashier account and a success toast confirms the action.
Reset service or network errorAn error toast explains that the reset request could not be completed. The Administrator can try again after the service is available.
Inactive or deleted accountThe Administrator must reactivate or recreate the account before the cashier can sign in.
Unauthorized userThe User Management page and its reset controls are unavailable to Cashier accounts.

The reset request does not sign the cashier into the dashboard. The cashier must complete the password change from the email link and then sign in with the updated password. Administrators may also use the account controls to edit, deactivate, reactivate, or delete user records according to their role and store policy.

4.2 Dashboard/Homepage

4.2.3 Analytics Card

Figure 4.6 — Analytics Card (Trend Tab)

The Analytics card consolidates four previously separate charts into a single tabbed surface. Each tab renders only when its tab is selected, which avoids painting four chart canvases simultaneously. The shared period selector drives all four views so that the user can compare different views over the same window.

The Trend tab renders a line chart of daily or weekly revenue depending on the selected period (daily for 7/30 days and single-month windows; weekly for 90 days; monthly for annual windows). The summary line above the chart leads with the total, the average per bucket, and the peak bucket.

Figure 4.7 — Analytics Card (Products Tab)

The Products tab renders a horizontal bar chart of the top five products by units sold in the selected period, with a subtitle showing order count, unit total, and the compare-period delta if enabled.

Figure 4.8 — Analytics Card (Categories Tab)

The Categories tab renders a doughnut chart of revenue by product category. A custom canvas plugin writes the top category's share (e.g., "42%") and its name into the doughnut hole. The legend lists every category with its exact revenue percentage.

Figure 4.9 — Analytics Card (Hours Tab)

The Hours tab renders a 7×17 heatmap — seven weekdays by the store's business hours (6 AM to 10 PM) — where each cell's color intensity represents the total revenue in that hour-of-week slot over the last 30 days. This view reveals peak business hours and slow periods at a glance.

4.2.4 AI Insights Card

Figure 4.10 — AI Insights (Forecast Tab)

The AI Insights card contains two tabs. The Forecast tab shows a 7-day revenue projection produced by the statistical forecasting engine. It displays a model pill (e.g., "linear regression"), a MAPE-based error pill, a trend indicator (Upward, Downward, Stable, or Low confidence), and a bar chart with one bar for each projected day. A short description explains that taller bars mean higher expected revenue and that the forecast is a guide, not a guarantee.

Figure 4.11 — AI Insights (Restock Tab)

The Restock tab ranks products by replenishment urgency using a 30-day sales velocity model. Each row shows the product name (with a slice label pill when applicable), a one-line reason string (e.g., "12 left · 6.0/day · min 20"), and a recommended order quantity. Urgency is color-coded: critical (red), high (amber), medium (blue), low (green).

4.2.5 Recent Activity Feed

Figure 4.12 — Recent Activity Feed

The Recent Activity feed lists the six most recent audit-log entries in reverse chronological order. Each row shows an action icon, the user's name, a one-line description, and a relative timestamp (e.g., "8 minutes ago"). The feed updates in real time as new events are recorded.

4.3 Main System Functions

This section demonstrates the core operational workflows visible in the web application: processing a sale, managing inventory, and using the Kirby assistant. Orders, customers, reports, and settings are demonstrated in the data-management and output sections that follow.

4.3.1 Point of Sale

Figure 4.13 — Point of Sale Interface

The POS page is a two-column layout: a product catalog on the left and the current order cart on the right. The catalog provides category filtering and product search. Products with size, brand, or other configured options require the cashier to select the appropriate variant before it is added to the cart.

Step-by-Step: Processing a Sale

  1. Navigate to the Point of Sale page from the sidebar.
  2. Optionally filter the catalog by category or type into the search field to narrow the product grid.
  3. Click a product card to add it to the cart. If the product has variants (e.g., sizes or brands), an inline selector appears; choose the desired variant.
  4. Repeat for additional products. Each unique product/variant combination forms its own cart line.
  5. Adjust quantities using the +/− steppers on each cart line, or by typing directly into the quantity input. The input clamps to the available stock level.
  6. Verify the subtotal, tax, and grand total in the cart totals panel. The tax rate is read from the store settings and is displayed on the tax label.
  7. Click Process Payment to open the payment modal.

Figure 4.14 — Payment Modal (Cash Payment)

  1. Optionally enter the customer's name and 11-digit phone number. Both fields are optional for cash payments.
  2. Select the payment method — Cash or GCash. Cash is selected by default.
  3. For cash payments, enter the amount received. The system computes and displays the change in real time and blocks submission if the received amount is less than the total.
  4. Click Complete Payment.
  5. The system runs a Firestore transaction that (a) checks the order does not already exist, (b) decrements stock for every line item, (c) writes the order document, and (d) writes an audit-log entry.
  6. The receipt modal appears with the finalized receipt.

Figure 4.15 — Receipt Modal

  1. Review the receipt — store header, receipt number, date, cashier name, itemized lines, subtotal/tax/total, payment details (cash or GCash reference), and the configurable footer.
  2. Click Print Receipt to open the browser's print dialog, or Done to close.

Step-by-Step: GCash Payment

Figure 4.16 — Payment Modal (GCash Payment)

  1. Follow steps 1–7 of the cash flow above.
  2. Select the GCash payment method. The system displays a QR code generated from the store's configured GCash number and account name.
  3. Both customer name and phone number become required. The labels are augmented with a red asterisk, and the confirm button is disabled until the required fields are filled.
  4. The cashier scans the QR with the customer's GCash app, or the customer scans with their own device. The amount to pay is shown above the QR.
  5. The customer provides the 13-digit reference number. The cashier types it into the GCash Reference Number field. Non-digits are stripped automatically; the field validates length live.
  6. Tick the I've received the payment and the reference number is correct confirmation checkbox. The Complete Payment button enables.
  7. Click Complete Payment. The system validates the reference number one final time, runs the Firestore transaction, and displays the receipt — which includes the GCash reference number.

Step-by-Step: Offline Sale

  1. Disconnect the device from the network (or simulate a server failure).
  2. The amber offline banner appears immediately at the top of the dashboard.
  3. Process a sale normally. The receipt is generated and displayed without delay — the user does not experience a failure.
  4. The sale is queued to localStorage.pos_order_queue and an informational toast appears: "Sale saved locally and queued to sync."
  5. Reconnect to the network. The heartbeat detects the connection, and a background flush replays the queued sale to Firestore.
  6. The offline banner disappears once the queue is empty.

4.3.2 Inventory Management

Figure 4.17 — Inventory Management Page

The Inventory page displays a statistics bar (Total Products, Over Stock, Low Stock, Out of Stock), a filter row (search, category, stock level), and a product table. The stat cards are clickable and act as quick filters — clicking "Low Stock" filters the table to low-stock products only.

Step-by-Step: Adding a New Product (Simple, No Variants)

  1. Click Add Product at the top-right of the Inventory page. The product modal opens.
  2. Optionally upload a product image. The system resizes the image to 400×400 JPEG on the client before embedding it in the document.
  3. Enter the product name, SKU, category, price, initial quantity, minimum stock level, and supplier.
  4. Leave the "This product comes in multiple options" checkbox unchecked.
  5. Optionally add a specification label (e.g., "2 in") that will display on the product card in the POS catalog.
  6. Enter a description.
  7. Click Save Product. The product is added to the table and the category is auto-selected if it was newly added.

Step-by-Step: Adding a Product with Variants (1 Option Group)

Figure 4.18 — Product Modal with Variant Editor

  1. Open the Add Product modal as above.
  2. Tick the This product comes in multiple options checkbox. The option editor appears and the shared quantity field hides.
  3. Choose the option name (e.g., "Size") from the dropdown.
  4. Enter the option values as a comma-separated list (e.g., 8 oz, 16 oz, 20 oz, 24 oz). The system renders each value as a chip below the input and generates a stock/price row for each.
  5. For each variant row, enter the stock count and (optionally) a per-variant price. If the price is left blank, the base price is used.
  6. The summary bar shows the total variant count, aggregate stock, and the price range.
  7. Click Save Product.

Step-by-Step: Adding a Product with 2 Option Groups (Matrix)

Figure 4.19 — Product Modal with Matrix Editor

  1. Open the Add Product modal and tick multiple options.
  2. Fill the first option group (e.g., "Size" with values S, M, L).
  3. Click + Add second option (e.g., brand) and fill the second group (e.g., "Brand" with values Bosch, Stanley).
  4. The system renders a matrix — one row per first-group value, one column per second-group value — with a stock/price cell for every intersection.
  5. Enter stock and price for each cell. Each cell is validated independently; an invalid entry blocks submission and highlights the cell.
  6. Click Save Product. The system stores the matrix as a variants object keyed by "size::brand".

Step-by-Step: Editing Product Stock

  1. Locate the product row in the table.
  2. For simple products, edit the inline quantity input and press Tab or Enter. The change is written to Firestore immediately.
  3. For variant products, click Edit and adjust individual variant stocks in the modal, then save.

Step-by-Step: Deleting a Product

  1. Click the trash icon on the product row.
  2. A confirmation modal appears with the product name and SKU.
  3. Click Delete. The product is removed from the catalog, the local cache, and Firestore; a deletion entry is written to the audit log with severity "warning".

4.3.3 Kirby Assistant

Figure 4.20 — Kirby Assistant Panel

Kirby is accessed via the floating action button at the bottom-right of every page. The panel is labeled Ask Kirby, slides out from the right edge, and contains a scrollable chat thread, a horizontal quick-prompt chip bar, and a text input at the bottom.

Step-by-Step: Asking a Structured Question

  1. Click the floating sparkle button at the bottom-right. The AI panel opens.
  2. Type a structured question (e.g., "How many Claw Hammers are left?") or click a quick-prompt chip (e.g., "What should I restock?").
  3. The message is sent to the backend, where the local NLP engine classifies the intent.
  4. Because the intent is recognized (inventory_check), a deterministic handler reads the relevant Firestore data and returns a structured response.
  5. The response appears in the chat thread with formatted values — money in green pills, stock keywords highlighted, and product names rendered as clickable buttons.

Figure 4.21 — Kirby Response to a Structured Question

Step-by-Step: Asking an Open-Ended Question

  1. Open the Kirby panel and type a free-form question (e.g., "Are we trending up or down this month?").
  2. The NLP engine does not find a specific intent, but recognizes the message as POS-relevant.
  3. The backend assembles a compact JSON snapshot of store aggregates — sales summaries, recent daily series, top products, inventory alerts — and forwards it to Gemini first, with Groq as the fallback provider.
  4. The provider produces a response grounded entirely in the provided snapshot. It is instructed to identify as Kirby, respond in the user's language, and never invent numbers.
  5. The response is rendered in the chat thread; provider metadata may be shown when returned by the API.

Step-by-Step: Asking an Unrelated Question

  1. Type a question outside the store and POS scope, such as a general knowledge, coding, or entertainment question.
  2. The backend identifies that the request is not POS-relevant and returns a local scope response instead of sending it to Gemini or Groq.
  3. Kirby explains that it is focused on store operations and suggests an inventory, sales, order, or transaction question.

Step-by-Step: Clicking a Product Name in a Response

  1. Any product name in an AI response appears as a highlighted button.
  2. Clicking the button closes the AI panel, navigates to the Inventory page, and pre-fills the inventory search field with that product name — narrowing the catalog to just that item.

Step-by-Step: Asking in Tagalog

  1. Type a Tagalog question (e.g., "Magkano benta ngayong linggo?").
  2. The NLP engine recognizes the Tagalog keywords (magkano, benta, ngayong linggo) and classifies the intent as sales_summary.
  3. The response is rendered in the same style as an English response. Deterministic handlers return a Tagalog translation, and when the LLM is invoked its prompt also requires the same language as the user — so a Tagalog question yields a Tagalog answer on either path.

4.4 Data Entry and Management

This section demonstrates the system's CRUD operations across its major entity types — Users, Customers, and Orders — plus the multi-filter data management surfaces (Audit Trail, User Management).

4.4.1 User Management (Administrator Only)

Figure 4.22 — User Management Page

The User Management page is restricted to the Administrator role. It lists every user profile with an avatar, name, email, role badge, active/inactive status, and last-login timestamp. Above the table, four stat cards show Total Users, Admins, Cashiers, and Inactive count.

Step-by-Step: Creating a New User

Figure 4.23 — Create User Modal

  1. Click Add User. The creation modal opens.
  2. Enter the new user's full name, email, and a password of at least six characters.
  3. Select the role — Cashier (default) or Admin. The Admin option is disabled automatically when the two-admin maximum is already reached.
  4. Enter the administrator's own password in the Your Admin Password field. This is required so that the system can restore the admin's session after creating the new Firebase Auth account.
  5. Click Create User.
  6. The system creates a Firebase Auth account for the new user, writes a profiles/{uid} document with the specified role, signs the new user out, and re-signs the admin back in.

Step-by-Step: Editing a User

  1. Click the pencil icon on the target user's row. The edit modal opens.
  2. Update the name, email, or role as needed.
  3. If any field was modified, the Your Admin Password field becomes required. Enter the current administrator's password.
  4. Click Save Changes. The system re-authenticates the admin, then updates the profile.
  5. Constraints are enforced: an admin cannot be demoted if they are the last active admin; the total admin count cannot exceed two.

Step-by-Step: Deactivating a User

  1. Click the user-slash icon on the target user's row.
  2. A confirmation modal appears with the account name and an explanation: "This user will be signed out on their next request and cannot sign in until reactivated."
  3. Enter the admin password.
  4. Click Deactivate. The profile's active field is set to false, and an audit entry is written.

4.4.2 Customer Management

Figure 4.24 — Customers Page

The Customers page lists all customer records with name, email, phone, order count, and lifetime spend. A search field filters by name, email, or phone.

Step-by-Step: Adding a Customer Manually

  1. Click Add Customer. Three sequential prompts appear: customer name (required), email (optional), and phone (optional).
  2. Enter the values. The record is written to Firestore and added to the local cache immediately.

In practice, however, the primary way customer records are created is automatically during a POS sale with a named customer — the system creates the record if it does not exist, or increments the order count and lifetime spend if it does.

Step-by-Step: Deleting a Customer

  1. Click the trash icon on the target customer's row.
  2. Confirm the deletion. The customer record is removed from Firestore and the local cache.

4.4.3 Order Management

Figure 4.25 — Orders Page

The Orders page lists every transaction with a status filter (All / Pending / Completed / Cancelled) and a date filter (All Dates / Today / This Week / This Month). Each row shows the receipt number, customer, items summary, total, status, and date. An "Actions" column provides a delete button.

Step-by-Step: Viewing Order Details

Figure 4.26 — Order Detail Modal

  1. Click on the items cell of any order. The order detail modal opens.
  2. The modal displays the receipt number (in monospace), customer name and phone, date, payment method (and GCash reference number if applicable), status, and total item count.
  3. Below the meta block, the itemized list shows each product with its size/brand variant and per-line total.
  4. The totals block shows subtotal, tax, and grand total.
  5. Click outside the modal or the close button to dismiss it.

Step-by-Step: Deleting an Order

  1. Click the trash icon on the target order's row.
  2. Confirm. The order is removed from Firestore and a warning-severity audit entry is written recording the deletion and the actor.

4.4.4 Audit Trail

Figure 4.27 — Audit Trail Page

The Audit Trail is the store owner's view into every action that occurred in the system. It is organized into four bands:

  1. Active Users panel — a live list of users currently signed in, derived from login/logout events within a 12-hour window.
  2. Owner stat cards — Sales Today, Staff Active Today, Deletions This Week, and Last Activity.
  3. Per-user summary — a per-staff breakdown of action counts, sales counts, sales totals, and deletions for today.
  4. Filterable log table — the full activity history with filters for search, time range, category, action type, and staff.

Step-by-Step: Filtering the Activity Log

  1. Use the Search field to filter by staff name, receipt number, customer name, or description text.
  2. Use the Time range dropdown to restrict to Today, Yesterday, Last 7 days, or Last 30 days.
  3. Use the Category dropdown to isolate a module (Sales, Inventory, Customers, Accounts, System).
  4. Use the What happened dropdown to filter by action type (Added, Changed, Removed, Signed in, Signed out, Exported).
  5. Use the Staff dropdown to view a single user's activity.
  6. Click Clear to reset all filters.

Step-by-Step: Exporting the Activity Log

  1. Click Export. A CSV file is generated containing timestamp, user, activity label, description, amount, and module for every log entry.
  2. The export itself is recorded as an audit event.

4.4.5 Settings

Figure 4.28 — Settings Page

The Settings page allows the administrator to configure store-wide information. Two sections are presented side by side on desktop and stacked on mobile:

  • Store Information — Store Name, Address, Contact Number, Receipt Footer.
  • Tax & Payments — Tax Rate (0–50%), GCash Number, GCash Account Name.

Step-by-Step: Updating Store Settings

  1. Navigate to Settings.
  2. Modify any of the fields. Hints below each field explain the intended use.
  3. Click Save Settings. The settings are written to config/settings in Firestore and broadcast to every open client via a custom event.
  4. The POS tax label, the receipt footer, and the GCash QR all update immediately without a page reload.

Step-by-Step: Resetting to Defaults

  1. Click Reset to Defaults.
  2. Confirm the dialog. All settings revert to the canonical defaults (store name, address, contact, footer, 8% tax rate, default GCash credentials).

4.6 Other features

Beyond the core operational modules, the system includes a set of supporting features that improve usability, resilience, and cross-device accessibility. These are enumerated below.

4.6.1 Dark and Light Theme Toggle

Figure 4.35 — Dark and Light Mode Comparison

The application supports two full themes — a warm charcoal dark mode and a warm ivory light mode — sharing the same structural tokens and accent color. The toggle is available in the top navigation bar on the dashboard and in the top-right corner of the login screen.

Theme switching is accompanied by a circular reveal animation centered on the selected toggle. The animation uses a lightweight CSS clip-path overlay, includes a reduced-motion fallback, and prevents repeated clicks from interrupting the transition. The chosen theme persists across reloads via localStorage.

4.6.2 Responsive Layout

Figure 4.36 — Mobile Layout (375px width)

The interface adapts to four breakpoints. On mobile (under 768px), the sidebar collapses to a slide-out drawer, tables convert to stacked card layouts, modals become bottom sheets, and tap targets are enlarged to a 44px minimum. The POS catalog switches to a single-column grid and the cart section moves below it.

4.6.3 Offline Operation

Figure 4.37 — Offline Banner with Pending Queue

When the network is unavailable — or when the API host is unreachable, as detected by a heartbeat — an amber banner appears below the navigation bar. The banner text adapts to the current state:

  • Offline with no queue: "You're offline — sales are queued and will sync automatically."
  • Offline with pending sales: "You're offline — N sales queued, will sync when online."
  • Back online with pending sales: "Back online — syncing N queued sales…"
  • Queue error: "N queued sales need attention: [error detail]."

4.6.4 Progressive Web App Installation

Figure 4.38 — PWA Installation Prompt

The system is installable as a Progressive Web App. On Chrome and Edge, an install prompt appears in the address bar. Once installed, the app launches from the device's home screen or app launcher, runs in its own window without browser chrome, and registers a service worker that caches the app shell for offline boot.

4.6.5 Notification Bell

Figure 4.39 — Notifications Panel

A bell icon in the top navigation bar shows a badge count of low-stock and out-of-stock items. Clicking the bell opens a dropdown panel listing up to eight of the most urgent items with their current quantity and minimum stock. A "View all in Inventory" link navigates directly to the Inventory page.

4.6.6 Service Worker Update Prompt

Figure 4.40 — New Version Available Toast

When a new version of the application is deployed, the service worker detects the change on the next visit and posts a message to the open tab. The application surfaces this as a dismissible toast: "A new version is available. Tap to reload." Clicking the toast activates the new service worker and reloads the page.

4.6.7 Audit-Based Active Users Panel

Figure 4.41 — Active Users Panel

The Audit Trail page includes an "active users" panel that derives current session state from login and logout events. Users who signed in within the last 12 hours and have not signed out are shown as active, along with the time since their sign-in and their total action count for the day. When no auth events exist in the recent log (e.g., after a database wipe), the panel falls back to showing all registered users as "Registered."

4.6.8 Stock-Slice Chip Display

Figure 4.42 — Per-Variant Stock Chips in the Inventory Table

For products with size or brand variations, the Inventory table's stock column does not display a single aggregate number. Instead, it renders one chip per variant, each showing the variant label and its stock count. Chips color-code automatically: green for healthy, amber for low, red for out of stock. A summary line at the bottom of the column shows the aggregate total.

4.6.9 Order-Detail Modal with GCash Reference

Figure 4.43 — Order Detail Modal for a GCash Order

When an order was paid via GCash, the order detail modal includes an additional row displaying the 13-digit GCash reference number in a monospace font, alongside the standard payment method label. This allows the owner to reconcile the store's GCash statement against the order history.

4.6.10 Receipts with Configurable Store Footer

Figure 4.44 — Receipt with Custom Footer

The receipt modal displays the store's name, address, and contact number at the top; a receipt number and transaction details; the itemized list; totals; the payment method (with GCash reference if applicable); the date and cashier name; and finally the store's configured footer text. All of these values are read from the store settings, so a change to the Settings page updates every future receipt immediately.

4.6.11 Toast Notification System

Figure 4.45 — Toast Notifications

The system uses a consistent toast notification pattern for user-facing feedback. Success toasts have a green left border; errors have a red border. Cart-update toasts are smaller and shorter-lived than operational toasts. Toasts appear in the bottom-right corner, stack vertically, and dismiss automatically after four seconds or on click.

4.6.12 Configurable Tax Rate Propagation

Figure 4.46 — Tax Rate Propagation

When the administrator changes the tax rate in Settings, the POS tax label updates within the same browser session without a reload. The system broadcasts a pos-settings-updated custom event that the POS module listens to; the tax label is re-read from localStorage and re-rendered. This ensures that the label always matches the actual tax applied at checkout.

4.6.13 Stale-Cache Recovery on Backend Failure

Figure 4.47 — Graceful Degradation When the Backend Is Unavailable

When the AI backend returns a server error, the client does not display raw provider text. Instead, the client shows a friendly connection message and the user can retry via the refresh button. Cached forecast and restock results may remain available, but new chat, forecast, and restock requests still require connectivity.

4.6.14 Login-Page Theme Toggle

Figure 4.48 — Theme Toggle on the Login Page

The theme toggle is also available on the login screen, so a user's theme preference can be established before they sign in. The toggle is positioned in the top-right corner of the viewport and hides once the dashboard loads.

4.6.15 Sidebar Collapse (Desktop)

Figure 4.49 — Collapsed Sidebar on Desktop

On desktop, the sidebar can be collapsed to a 72px icons-only strip via the toggle button next to the logo. This gives a wider content area on smaller laptop screens or when working with wide tables. The collapsed state persists across reloads.

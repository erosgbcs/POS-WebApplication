Chapter 2: System analysis and Design

2.1 Existing system/Process

Kirby's Hardware is a small-scale retail hardware store that has historically operated using fully manual processes. The store's day-to-day operations have relied on paper-based tracking, handwritten receipts, and mental arithmetic — a workflow that has proven adequate for very low transaction volumes but that breaks down as the business grows.

2.1.1 Description of the Current Manual Process

Prior to the development of the proposed system, the store's operations were divided into the following manual procedures:

Inventory Tracking. Stock levels are recorded in a handwritten ledger or notebook. When a shipment arrives, the store owner manually writes the new quantity next to each product's existing entry. When a sale occurs, the cashier is expected to subtract the sold quantity by hand. There is no systematic verification, and no early-warning mechanism for low stock — the owner discovers an item is out of stock only when a customer asks for it and it cannot be found on the shelf.

Sales Transactions. Each sale is recorded on a carbon-copy receipt pad. The cashier manually computes line totals, applies a mental or calculator-based tax calculation, and hands the customer a handwritten receipt. The carbon copy is filed for later tallying, but there is no consistent daily reconciliation and no aggregated view of revenue across a period.

Product Pricing. Prices are posted on a whiteboard or marked on shelf labels. When a price changes, the owner must update every label by hand. There is no historical record of price changes, and no way to verify what price was charged on a specific date.

Customer Records. The store occasionally keeps the names and contact numbers of regular customers in a small address book. Repeat purchases are not tracked. There is no way to identify a customer's lifetime spend, order frequency, or preferred products.

Reporting. At the end of each day, the owner counts the cash drawer against the carbon-copy receipts. At the end of the month, sales totals are compiled by manually summing dozens of receipts. Generating a report for a specific week, month, or product category requires hours of manual arithmetic.

Staff Oversight. When more than one person operates the store, the owner has no reliable way to verify which employee performed a given transaction, made a pricing change, or deleted a record. There is no audit trail and no accountability mechanism beyond personal trust.

2.1.2 Problems Identified in the Current System

Problem Area Specific Issue
Inventory accuracyManual stock updates drift from reality over time. Shrinkage and miscounts go undetected until a stock-out occurs.
Low-stock detectionNo mechanism notifies the owner when a product falls below a threshold. Restocking is reactive, not proactive.
Sales reportingGenerating any period-based report requires manual compilation that is error-prone and slow.
Transaction tracingCarbon-copy receipts cannot be searched. Finding a specific sale from three months ago is practically impossible.
Customer relationshipRepeat customers are not tracked. The store cannot identify its top buyers or measure lifetime value.
Staff accountabilityNo audit log means any employee action is untraceable.
Business intelligenceThe owner has no data to base decisions on — no sales trends, no seasonality, no product performance ranking.
Physical record lossPaper receipts and ledgers are vulnerable to water damage, fire, loss, and simple misplacement.

These problems collectively limit the store's ability to scale, to make data-driven decisions, and to operate reliably as transaction volume increases.

2.2 Proposed System

The proposed system — Kirby's Hardware POS and Inventory Management System — is a browser-based point-of-sale and inventory management platform designed specifically for the operational realities of a small Philippine hardware store. It replaces the manual workflow with a responsive single-page application accessible from a laptop, tablet, or smartphone without requiring dedicated POS hardware. Firebase Authentication and Cloud Firestore provide the identity, data, synchronization, and offline persistence services, while Vercel hosts the static frontend and protected Python API functions.

2.2.1 System Overview

The proposed system consolidates seven previously-separate manual processes into a single integrated application:

  1. Point of Sale — replaces the carbon-copy receipt pad with an interactive cart and payment interface that writes structured order documents to a cloud database.
  2. Inventory Management — replaces the handwritten ledger with a searchable, filterable catalog that supports size/brand variant matrices, product images, and automated low-stock detection.
  3. Order History — replaces the physical receipt archive with a searchable table of every transaction.
  4. Customer Tracking — replaces the address book with a structured customer database that automatically aggregates order count and lifetime spend.
  5. Audit Logging — introduces an activity trail that records every sale, login, inventory change, and settings update with a timestamp and the user responsible.
  6. Reporting & Analytics — replaces manual month-end arithmetic with one-click CSV and PDF exports and live dashboards.
  7. AI Assistant — provides a conversational interface that answers natural-language questions about the store's operations.

2.2.2 Key Innovations

Offline-capable operation. Firestore's browser persistence caches supported application data and queues supported writes in IndexedDB. POS sales also use an application-level localStorage.pos_order_queue so eligible network-failed sales can be queued and replayed when connectivity returns. Authentication, API chat, forecasting, and other server-dependent operations still require connectivity or previously cached data.

No dedicated hardware. The entire system runs in a web browser. The store does not need to purchase a specialized POS terminal — an existing laptop, tablet, or even a smartphone is sufficient.

Real-time multi-device sync. Because Firestore pushes changes to connected clients, a successfully synchronized sale can appear on another connected device shortly after it is recorded. Offline or queued sales appear after synchronization completes.

Kirby AI integration. Kirby first classifies supported requests on the server and uses deterministic handlers for structured POS questions. Local handlers and LLM responses follow the user's English or Tagalog/Taglish language. Only POS-relevant open-ended questions are sent to Gemini, with Groq as the fallback provider; unrelated questions are redirected rather than answered as general chat.

Statistical sales forecasting. Rather than relying on the LLM for numeric predictions, the system uses a pure-Python forecasting engine that scores four candidate statistical models via rolling-origin cross-validation and returns a 7-day forecast with 95% prediction intervals. The Forecast tab presents one bar per projected day and explains that taller bars represent higher expected revenue.

2.4 System Features

The system delivers the following major features, grouped by functional area.

2.4.1 Authentication & Access Control

  • Secure login via Firebase Authentication (email + password)
  • Role-based access control with two roles: Administrator and Cashier
  • Deactivated-account rejection at sign-in
  • Administrator-controlled cashier password reset via email link
  • Session persistence across page reloads and offline periods
  • Two-admin maximum with a minimum of one active admin enforced at the UI level

2.4.2 Point of Sale

  • Product catalog with category filter and search
  • Variant selection for products with size and/or brand options
  • Cart management with quantity steppers, per-line remove, and clear-cart
  • Live totals with configurable tax rate
  • Payment processing for Cash and GCash
  • GCash QR generation from configured number and account name
  • GCash reference validation — 13-digit numeric
  • Stock validation at cart-add time and again at checkout
  • Printable receipt with store header, footer, cashier name, and receipt number
  • Offline sale queueing with automatic sync on reconnect

2.4.3 Inventory Management

  • Product CRUD with name, SKU, category, price, min-stock, supplier, and description
  • Product images with client-side resizing to 400×400 JPEG
  • Option groups — supports 0, 1, or 2 option dimensions
  • Variant matrices with per-variant stock and optional per-variant pricing
  • Stock badge states — In Stock, Low Stock, Out of Stock, Over Stocked
  • Clickable stat cards that filter the table
  • Category management with inline "add new category"
  • CSV export of the full inventory
  • Paginated table with 10 rows per page

2.4.4 Orders Module

  • Order table with status and date filters
  • Order detail modal showing receipt number, customer, phone, date, payment method, GCash reference, and per-line items
  • Order deletion with audit logging
  • Timezone-correct "Today" filter — start-of-day in Asia/Manila

2.4.5 Customers Module

  • Customer CRUD with name, email, phone
  • Automatic aggregation of order count and lifetime spend
  • Auto-sync on POS sale — placing an order with a named customer updates their record atomically
  • Search across name, email, and phone

2.4.6 Audit Trail

  • Every action logged with timestamp, user, module, action, and description
  • Owner-friendly labels — "Sale" instead of transaction:pos
  • Filters — search, staff, time range, category, and action type
  • Active users panel derived from login/logout events
  • Per-user daily summary showing action counts, sales totals, and deletion counts
  • CSV export of the activity log

2.4.7 Reports & Analytics

  • Sales, Inventory, Customer, Financial reports
  • CSV and PDF export for each report type
  • Period selector — Today, Yesterday, Last 7/30 days, This/Last Month, This/Last Year, Custom range
  • Overview charts — 4 tabbed analytics: revenue trend, top products, category breakdown, hourly heatmap
  • Live KPI cards — Today's Sales, Orders Today, Products in Stock, Active Customers

2.4.8 AI Assistant

  • Deterministic NLP intent classifier — 13 intents recognized before any LLM call
  • Local handlers for structured queries (low stock, top sellers, today's sales, etc.)
  • Kirby LLM fallback — Gemini primary and Groq fallback for POS-relevant open-ended questions; unrelated questions are redirected locally
  • Compact context injection — the LLM receives only aggregated JSON
  • Sales forecasting — statistical 7-day projection with confidence intervals
  • Restock recommendations — ranked by urgency using 30-day sales velocity
  • Clickable product names that navigate to the inventory search
  • Bilingual support — responds in Tagalog / Taglish if the user writes in Tagalog / Taglish
  • Persistent chat history across page reloads

2.4.9 User Management

  • Create new users with role assignment
  • Edit user profile — name, email, role
  • Password reset email dispatch for cashier accounts by an Administrator
  • Deactivate / reactivate accounts
  • Delete profile records
  • Admin confirmation is required for user-management actions that expose a confirmation step; password-reset email dispatch uses the selected account's registered email
  • Search, filter by role, filter by status
  • Paginated table with 10 rows per page

2.4.10 Settings

  • Store information — name, address, contact number
  • Receipt footer configuration
  • Tax rate configuration (0–50%)
  • GCash credentials — number and account name
  • Reset to defaults option
  • Live propagation — settings changes broadcast to all open tabs

2.4.11 System-Wide Features

  • Dark / Light theme with a CSS clip-path circular reveal animation and reduced-motion fallback
  • Fully responsive layout — desktop, tablet, and mobile
  • Offline banner that appears whenever the network is unavailable or sales are queued
  • Service Worker for PWA installation and offline app-shell caching
  • Notification bell with badge count for low-stock items
  • Auto-update prompt when a new app version is deployed

The use case diagram identifies the two primary actors — Cashier and Administrator — and the operations each can perform. 2.5.1 Actor Descriptions

Actor Description
Cashier A store employee responsible for day-to-day customer transactions. Can process sales, view orders, manage customers, view dashboards and reports, and interact with the AI assistant. Cannot modify inventory, manage users, view audit logs, or change settings.
Administrator The store owner or trusted manager. Has all cashier capabilities plus administrative access to inventory CRUD, user management, audit trail, and system settings.

2.5.2 Use Case Descriptions

UC-01: Log In

Actors: Cashier, Administrator
Precondition: The user has a valid account in Firebase Authentication.
Main Flow: (1) User enters email and password. (2) System validates the credentials via Firebase Auth. (3) System retrieves the user's profiles/{uid} document. (4) System checks the active flag. (5) System loads the dashboard with role-appropriate navigation.
Alternate Flow: If the profile is marked inactive, the system signs the user out and displays "This account has been deactivated."

UC-02: Process Sale

Actors: Cashier, Administrator
Precondition: The user is logged in and the product catalog is loaded.
Main Flow: (1) Cashier selects products from the catalog. (2) System adds items to the cart with the correct price. (3) Cashier clicks Checkout. (4) System displays the payment modal with the total. (5) Cashier selects payment method and enters payment details. (6) System runs a Firestore transaction that decrements stock and writes the order document. (7) System displays a printable receipt.
Alternate Flow: If a supported network failure occurs, the sale is queued locally and the receipt is generated. Validation, stock, payment, and other permanent errors are displayed and are not silently queued.

UC-03: Manage Inventory

Actors: Administrator only
Main Flow: (1) Admin navigates to the Inventory page. (2) System displays the product catalog table. (3) Admin can add, edit, or delete products. (4) For products with options, the admin configures option groups and variant stock in a matrix editor. (5) Changes are written to Firestore and audited.

UC-04: View Reports & Export

Actors: Cashier, Administrator
Main Flow: (1) User navigates to the Reports page. (2) User selects a report period. (3) User clicks a report type. (4) System builds the report data from local cache. (5) System triggers a CSV download or opens a print-ready PDF.

UC-05: Ask AI Assistant

Actors: Cashier, Administrator
Main Flow: (1) User opens the AI panel. (2) User types a natural-language question. (3) System classifies the intent locally. (4) If a deterministic handler exists, the system answers from Firestore aggregates. (5) If the intent is unknown but POS-relevant, the system forwards a compact context snapshot to Gemini, falling back to Groq if Gemini is unavailable.

UC-06: Manage Users

Actors: Administrator only
Main Flow: (1) Admin navigates to the User Management page. (2) System lists all profiles. (3) Admin creates, edits, deactivates, reactivates, or deletes a user. (4) Sensitive operations require admin password re-authentication. (5) Changes are audited.

UC-07: View Audit Trail

Actors: Administrator only
Main Flow: (1) Admin navigates to the Audit Trail page. (2) System displays the activity log table. (3) Admin can filter, search, and export the log.

2.8.4 Relationships and Referential Integrity

Because Firestore does not enforce foreign keys, the application maintains referential integrity through the following rules:

  • profiles.id ↔ Firebase Auth UID. The document ID is always set to the Firebase UID at account creation, ensuring a 1:1 mapping.
  • orders.items[].productId → inventory.id. Each line item stores the product's document ID.
  • audit_logs.user ↔ profiles.full_name. The audit log stores the actor's display name, not a strict foreign-key reference to the profile.
  • customers.orders / totalSpent ↔ orders. Denormalized counters updated atomically on every POS sale.

2.8.6 Security Rules

Firestore Security Rules provide an authenticated database access boundary, while role-based page visibility and administrator checks are also enforced by the application. The rules shown below are a simplified documentation example and must be kept synchronized with the deployed Firebase rules.

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // Only authenticated users can read/write anything.
    match /{document=**} {
      allow read, write: if request.auth != null;
    }

    // Profiles: self-create only; role/active mutations require admin.
    match /profiles/{userId} {
      allow read: if request.auth != null;
      allow create: if request.auth.uid == userId;
      allow update, delete: if request.auth != null && isAdmin();
    }

    // Orders: any authenticated user can create; only admin can delete.
    match /orders/{orderId} {
      allow read, create, update: if request.auth != null;
      allow delete: if request.auth != null && isAdmin();
    }

    // Audit logs: append-only for regular users.
    match /audit_logs/{logId} {
      allow read, create: if request.auth != null;
      allow update, delete: if request.auth != null && isAdmin();
    }

    function isAdmin() {
      return request.auth != null
        && get(/databases/$(database)/documents/profiles/$(request.auth.uid)).data.role == 'admin';
    }
  }
}

Figure 2.10 — Firestore Security Rules

These rules guarantee that:

  • Unauthenticated requests are rejected at the database layer, not just the application layer.
  • Users can only create their own profile (during signup) but cannot promote themselves.
  • Order deletion is restricted to administrators.
  • Audit log entries are protected from modification or deletion by non-admins under the documented rule set.

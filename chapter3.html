Chapter 3: System Development and Implementation

3.1 Development Tools and Technology

The Kirby's Hardware POS and Inventory Management System was developed using a modern serverless technology stack chosen for reliability, low operational cost, and rapid deployment. The following tools and technologies were utilized:

3.1.1 Programming Languages

JavaScript (ES2022) — Serves as the primary client-side language. The application is built in vanilla JavaScript without a front-end framework (React, Vue, Angular), which minimizes bundle size, eliminates build-step complexity, and keeps the codebase directly readable and auditable. All application logic — POS transaction handling, inventory state management, chart rendering, AI assistant orchestration, and offline synchronization — is written in modular IIFE-scoped files.

Python 3.11 — Powers all server-side functions deployed as Vercel Serverless Functions. Python was selected for its mature ecosystem of data-science libraries (used in the forecasting module), its straightforward Firestore Admin SDK bindings, and its concise syntax for API integration work.

HTML5 and CSS3 — Used for markup and styling. Tailwind CSS v4 provides utility-class-based styling for the custom component layer, while a large hand-authored style.css handles theme tokens, animations, responsive breakpoints, and dark/light mode.

3.1.3 Database

Cloud Firestore — A NoSQL document database used for all persistent application data. Firestore was chosen over a relational database for three reasons:

  1. Real-time synchronization — Firestore's onSnapshot API pushes live updates to every connected client, enabling the Overview dashboard to reflect new orders, inventory changes, and audit events without polling.
  2. Offline persistence — The Firestore client SDK stores writes in IndexedDB during network loss and replays them automatically on reconnect. This is critical for a POS terminal that must remain operational during internet outages.
  3. Serverless-native scaling — No connection pooling, no capacity provisioning, no schema migrations. The database scales automatically with demand.

The database contains five primary collections: inventory, orders, customers, audit_logs, and profiles, plus a config collection for store settings.

3.1.4 Integrated Development Environment

Visual Studio Code with the following extensions: Python, Pylance, ESLint, Prettier, and the Firebase Explorer. All source code is version-controlled with Git and hosted on GitHub, with automatic deployment to Vercel on every push to the main branch.

3.1.5 Deployment Platform

Vercel — A serverless hosting platform used for both the static front-end (HTML/JS/CSS bundle served via CDN edge nodes) and the Python API layer (functions auto-scaled per request). Vercel was chosen for its zero-configuration deployment workflow, automatic HTTPS, preview deployments for every branch, and native support for Python serverless functions.

3.2 System Architecture

The system is documented using a three-layer serverless architecture: a browser client with Firebase/local persistence, an edge-served static frontend and Python API layer, and managed Firebase/Firestore plus external AI services. This is a logical documentation model; several client and cloud services operate directly alongside the API layer.

3.2.2 Component Interaction

Authentication Flow. A user signs in via the login form. Firebase Auth validates credentials and issues a signed ID token (JWT). The client stores the token and attaches it to every subsequent API request as Authorization: Bearer <token>. The Python backend verifies the token using the Firebase Admin SDK and loads the caller's profile document to enforce role-based access control.

POS Transaction Flow. When a cashier completes a sale, pos.js:

  1. Runs a Firestore runTransaction() that atomically decrements supported stock fields and writes the order document.
  2. If a supported network failure occurs, the sale is queued to localStorage.pos_order_queue and replayed when connectivity returns; permanent validation and unsupported-variant failures remain visible errors.
  3. The receipt is displayed immediately from local state — the user never waits for the network.

Kirby Assistant Flow. When a user submits a chat message:

  1. nlp_engine.py first attempts local intent classification (deterministic keyword matching with fuzzy product lookup).
  2. If the intent is matched, a predefined handler returns structured data without touching an LLM.
  3. If the intent is unknown but the message is POS-relevant, the backend assembles a compact JSON snapshot of store aggregates and forwards it to Gemini (primary) or Groq (fallback). Unrelated messages receive a local scope response and are not sent to either provider.

Real-Time Sync Flow. Firestore onSnapshot subscriptions push updates to every open tab as data changes. The dashboard's scheduleOverviewRefresh() debounces rapid bursts into a single render, preventing redundant chart rebuilds and AI proxy calls.

3.2.3 Design Decisions

The architecture is offline-capable: Firestore's client SDK persists cached data and queues supported writes in IndexedDB, while the POS adds a dedicated localStorage queue for sales that need explicit replay and status feedback. This allows the terminal to continue key POS work through temporary internet outages without claiming that every server operation is available offline.

The backend is stateless: no session state, no in-memory cache between requests, no long-running processes. Each Python function cold-starts on demand, reads configuration from environment variables, and exits after responding. This makes the system horizontally scalable by construction.

The AI layer is opportunistic: Kirby uses local deterministic intent handling for known POS requests. Gemini and Groq are treated as a fallback for POS-relevant open-ended questions only; the shared prompt requires the providers to identify as Kirby, use only supplied store data, respond in the user's language, and redirect unrelated requests.

3.3 User Interface Design

The interface follows a dashboard-and-sidebar layout pattern commonly used in business management software. The design prioritizes legibility under varying lighting conditions (for a physical store environment), fast numeric scanning, and touch-friendly controls on mobile devices.

3.3.1 Design Principles

  1. Single palette, dual theme. A warm amber accent (#FACC15 dark / #E0A300 light) with a neutral charcoal/ivory surface. Dark and light themes share the same structural tokens and are switchable via a CSS clip-path circular reveal animation.
  2. Data-first density. Numeric values use a tabular-numeric font variant and are displayed at scale (32px KPI numbers, 24px stat numbers) so a manager can read the dashboard at a glance.
  3. Progressive disclosure. Complex surfaces (Analytics, AI Insights) are consolidated behind tabs. The Overview page shows one chart at a time; the four analytics views (Trend, Products, Categories, Hours) and two AI views (Forecast, Restock) each have their own tab.
  4. Offline transparency. An amber banner appears when the browser is offline or queued sales exist, informing the cashier without blocking eligible work.

3.3.2 Primary Screens

Login Screen. Two-panel layout with a brand panel on the left (logo, store name, session status indicator) and an authentication card on the right. Includes an email/password form with show-password toggle, a "Remember me" checkbox, and guidance that cashier password resets must be requested from an Administrator.

Overview Dashboard. The landing page after login. Contains:

  • A header with four quick-action buttons (New Order, Add Product, Report, Manage Users)
  • A "Needs Attention" strip that surfaces low-stock, out-of-stock, and offline-queued items
  • Four KPI cards (Today's Sales, Orders Today, Products in Stock, Active Customers) with delta indicators
  • A tabbed Analytics card (Trend / Products / Categories / Hours)
  • A two-column grid containing the AI Insights card (Forecast / Restock tabs) and a Recent Activity feed

Point of Sale. A two-column layout: a searchable product catalog on the left with category filtering, and the current order cart on the right. Products with size/brand variants open an inline selector on click. The cart displays unit prices, per-line totals, subtotal, tax, and grand total, with quantity steppers and per-line remove buttons.

Inventory Management. A statistics bar (Total / Over Stock / Low Stock / Out of Stock), a filter row (search, category, stock level), and a paginated table listing products with thumbnails, category, price, stock (with per-variant chips for optioned products), status badge, last-updated timestamp, and edit/delete actions.

Payment Modal. Triggered by Checkout. Displays the total, customer information fields (optional for cash, required for GCash), payment method selector, cash-received input with live change calculation, and a GCash QR block with a required 13-digit reference number field and confirmation checkbox.

Receipt Modal. Displays a formatted printable receipt with store header, receipt number, itemized list, subtotal/tax/total, payment details, cashier name, and configurable footer text. A print button opens the browser's native print dialog.

Audit Trail. A read-only activity log with filter controls (search, staff, time range, category, action type), a sortable table of events, and a per-user activity summary. Every sale, login, inventory change, and settings update is recorded here.

Reports. Four report cards (Sales, Inventory, Customer, Financial), each offering CSV and PDF export. A period selector filters the sales and financial reports by today, yesterday, last 7/30 days, this/last month, this/last year, or a custom date range.

User Management. An admin-only screen listing all staff accounts with role badges, status indicators, last-login timestamps, and actions (edit, password reset, deactivate, delete). New accounts are created via a modal form that requires admin password re-authentication.

Kirby Assistant Panel. A slide-out drawer from the right edge containing a scrollable chat thread, a horizontal quick-prompt chip bar, and a text input. Kirby can answer open-ended questions about sales, stock, customers, and trends; structured questions are handled by the local NLP engine, while unrelated questions are redirected to the store-focused capabilities.

3.4 System Modules

The system comprises eleven functional modules, each encapsulated in its own source file and exposing a narrow public API.

3.4.1 Authentication Module (auth.js)

Handles user sign-in, administrator-controlled cashier password-reset email dispatch, session persistence, and role-based access control. Uses Firebase Authentication (email/password) as the identity provider. On successful sign-in, fetches the user's profiles/{uid} document from Firestore to determine role (admin or cashier). Enforces:

  • Two-admin maximum (a lightweight policy constraint implemented client-side)
  • Deactivated-account rejection at sign-in
  • Firebase ID token refresh on every API call

Session state is cached in localStorage and re-hydrated on page load, with role-based navigation visibility applied immediately. Admin-only pages (Users, Settings, Audit Trail) are hidden from cashiers.

3.4.2 Firebase Integration Module (firebase.js)

Wraps the Firebase Web SDK behind a namespaced API (window.POS_FIREBASE / window.POS_SUPABASE). Provides:

  • Auth operations: signUpUser, signInUser, signOut, getCurrentUser, resetPassword, getIdToken
  • Inventory CRUD: getInventoryProducts, addInventoryProduct, updateInventoryProduct, deleteInventoryProduct, getInventoryStats
  • Order operations: commitSale (atomic transaction with stock decrement for supported simple and legacy size-stock records), getOrders, deleteOrder, subscribeOrders
  • Customer operations: getCustomers, addCustomer, updateCustomer, deleteCustomer, subscribeCustomers
  • Audit logging: addAuditLog, getAuditLogs, clearAuditLogs, subscribeAuditLogs
  • Config: getSettings, saveSettings, getCategories, saveCategories

Firestore is initialized with persistentLocalCache and persistentMultipleTabManager, enabling offline writes and cross-tab consistency. All subscriptions return an unsubscribe function.

3.4.3 Inventory Management Module (inventory.js)

Manages product catalog CRUD, variant matrices, category management, stock-level updates, CSV export, and pagination. Supports a unified 0/1/2 option-group model:

  • 0 options: single-quantity products (e.g., Cement)
  • 1 option: single-axis variants (e.g., Hammer by size)
  • 2 options: size × brand matrices with per-variant stock and optional per-variant pricing

Legacy shapes (sizeStocks, brandStocks, older variant formats) are normalized on read and preserved through the new model, ensuring backward compatibility with existing Firestore documents.

Product images are resized client-side to 400×400 JPEG (quality 0.78) before being Base64-encoded into the Firestore document — avoiding the operational cost of a separate storage bucket for a small-scale deployment.

3.4.4 Point of Sale Module (pos.js)

Handles the entire transaction lifecycle:

  1. Product catalog rendering with lazy category filtering to avoid painting hundreds of DOM nodes
  2. Inline variant selection via dynamically generated <select> elements
  3. Cart state management with per-line price tracking (necessary for per-variant pricing)
  4. Stock validation at both cart-add time and checkout time to prevent overselling
  5. Payment processing for cash and GCash
  6. Receipt generation with configurable store header, footer, tax rate, and GCash reference number
  7. Offline queueing — eligible network-related sale failures are pushed to localStorage.pos_order_queue and replayed on reconnect with idempotency guaranteed by order ID; validation, variant-model, and business-rule failures remain visible errors

The module runs a live subscription to Firestore so that catalog stock decrements reflect immediately across every open tab.

3.4.5 Orders Module

Renders the orders table with status and date filters, opens a detailed modal for any order showing the receipt number, customer, phone, date, payment method, GCash reference (if applicable), and itemized line items with per-line totals. Supports order deletion with audit logging. Uses store-timezone-aware date filtering so "Today" means start-of-day in Asia/Manila, not a rolling 24-hour window.

3.4.6 Customers Module

CRUD for customer records with name, email, phone, order count, and lifetime spend. Deleting a customer removes the Firestore document and updates the local cache. Customer records are auto-synced when a POS order is placed with a named customer — the order count and lifetime spend are incremented atomically.

3.4.7 Audit Trail Module (audit.js)

Records every meaningful action in the system with timestamp, user, action type, module, description, and severity. Renders a filterable, searchable log view that translates raw action codes (e.g., create:inventory) into owner-friendly labels (e.g., "Added product"). Includes an active users panel that derives session state from login/logout events within a 12-hour window, falling back to registered profiles when no auth events exist.

Every POS sale writes an audit entry with the full transaction payload (receipt ID, item count, total, payment method, customer name), enabling the store owner to reconcile daily totals against the log.

3.4.8 Reports Module

Provides four report types (Sales, Inventory, Customer, Financial), each exportable as CSV or as a print-ready PDF. The PDF exporter builds a self-contained HTML document with embedded CSS, opens it in a new window, and triggers window.print() — letting the user choose "Save as PDF" without requiring a server-side PDF library.

Reports honor the currently selected period via a shared getActiveReportRange() function that returns { start, end, label, key } for any preset or custom date range. Filenames include the period slug so multiple exports don't overwrite each other.

3.4.9 User Management Module

Admin-only. Lists all Firebase Auth users alongside their Firestore profiles/{uid} records. Actions include:

  • Create user: creates a Firebase Auth account, writes a profile document, and re-signs-in the admin to preserve their session
  • Edit user: updates profile fields (name, email, role) with password re-authentication
  • Reset password: sends a Firebase password-reset email
  • Deactivate / reactivate: toggles the active flag on the profile
  • Delete: removes the Firestore profile only (Firebase Auth deletion requires manual Console action)

Constraints enforced: maximum two admin accounts, minimum one active admin.

3.4.10 Settings Module

Reads and writes the config/settings Firestore document. Manages:

  • Store name, address, contact number
  • Receipt footer text
  • Tax rate (0–50%)
  • GCash number and account name

Settings changes are broadcast to all live components via a pos-settings-updated custom event, causing the POS tax label, receipt footer, and GCash QR to refresh without a page reload.

3.4.11 AI Assistant Module (ai.js + _lib/*.py)

The most architecturally complex module. It is split between client orchestration and server execution:

Client (ai.js) — Manages chat history persistence, 6-hour AI response caches, in-flight request deduplication, friendly error handling, and targeted cache invalidation. Chat questions are not queued offline; chat, forecasting, and restock requests require the server.

Server (_lib/ai_providers.py) — Abstracts the LLM layer with two providers:

  • Gemini (primary, gemini-3.8-flash) — tried first with a 6-second timeout and one retry on retryable status
  • Groq (fallback, openai/gpt-oss-20b) — used when Gemini fails, times out, or is missing credentials

Server (_lib/nlp_engine.py) — A deterministic intent classifier that runs before any LLM call. Recognizes thirteen intents (greeting, help, low_stock, out_of_stock, inventory_check, product_search, daily_sales, sales_summary, sales_history, best_seller, transaction_history, sales_forecast, restock_recommendation) using weighted keyword and phrase matching with fuzzy product-name resolution. The classifier includes English and Tagalog/Taglish vocabulary.

Server (_lib/handlers.py) — Implements each intent as a pure function over Firestore data. Handlers never invent numbers; if data is unavailable, they return an honest error. Deterministic responses are localized to English or Tagalog/Taglish from the detected user language. The AI system prompt (for the LLM fallback) explicitly forbids hallucinating values and instructs the model to reply with a specific refusal phrase when the provided context is insufficient.

Server (_lib/forecasting.py) — Pure-Python sales forecasting. Scores four candidate models (historical mean, moving average, seasonal naive, linear regression) using rolling-origin cross-validation with a 1% one-standard-error preference toward simpler models. Returns a 7-day point forecast with 95% prediction intervals.

3.5 System Implementation

3.5.1 Development Workflow

The system was developed iteratively with the following process:

  1. Feature specification — each feature was described in plain language with expected inputs and outputs
  2. Isolated implementation — features were built as self-contained modules to reduce cross-module coupling
  3. Client-first testing — business logic was validated in the browser console before wiring it to the UI
  4. Progressive enhancement — offline behavior, error handling, and AI fallbacks were added after the happy-path implementation worked
  5. Continuous deployment — every push to main triggered an automatic Vercel deployment, with preview URLs available for every branch

3.5.2 Deployment Architecture

The application is deployed on Vercel with the following topology:

Static assets (index.html, *.js, *.css, assets/)
  → Vercel Edge Network (global CDN, automatic HTTPS, HTTP/2)

API functions (api/*.py)
  → Vercel Serverless (Python 3.11 runtime, one container per cold start)

Environment variables
  → FIREBASE_SERVICE_ACCOUNT_JSON  (Firestore Admin credentials)
  → GEMINI_API_KEY                  (primary LLM)
  → GROQ_API_KEY                    (fallback LLM)
  → GEMINI_MODEL, GROQ_MODEL, GEMINI_TIMEOUT_S, GROQ_TIMEOUT_S  (optional overrides)

The service worker (sw.js) precaches the app shell on first load and handles subsequent requests with cache-first semantics for same-origin assets and versioned CDN libraries. API calls bypass the cache entirely — Firestore and Firebase Auth have their own IndexedDB offline layer.

3.5.3 Authentication Implementation

The Firebase ID-token verification flow is implemented in _lib/auth.py. Every protected endpoint:

  1. Reads the Authorization: Bearer <token> header
  2. Calls firebase_admin.auth.verify_id_token(token)
  3. Loads the caller's profiles/{uid} document
  4. Rejects the request if the profile is missing or the active flag is false

Role checks are layered on top: require_admin(uid) enforces role == "admin" for administrative operations. No role or user ID is ever trusted from the request body.

3.5.4 Data Consistency

Transactional writes. POS sales use Firestore's runTransaction() for supported simple and legacy size-stock records, guaranteeing that either stock is decremented and the order is written, or neither happens. The transaction also acts as an idempotency barrier: if an order with the same receipt number already exists, the transaction exits without double-decrementing stock. The newer matrix-shaped variants data requires the application variant path and is not described as transactionally supported here.

Idempotent replay. When an offline order is synced, the same transaction semantics apply. A sale that was already committed (perhaps the network failed during response transmission) does not duplicate. The orderId derived from the receipt number acts as the natural key.

Timezone correctness. All date bucketing uses Asia/Manila (UTC+8) as the reference timezone. "Today" in the dashboard, the orders filter, the sales report, and the audit log all mean start-of-day Manila — not UTC and not the browser's local timezone.

3.5.6 Offline Support

Offline behavior is implemented at three levels:

Firestore's built-in offline layer — Writes made while offline are stored in IndexedDB and replayed automatically when the connection returns. This handles the majority of network transients without any custom code.

Application-level pending queue — For eligible network-related sales, pos.js maintains a pos_order_queue in localStorage. A background flusher replays queued sales on reconnect. Validation, stock, unsupported-variant, and other permanent failures remain visible instead of being treated as offline sales.

Effective-online detection — navigator.onLine lies on captive portals and when the API host is unreachable. A heartbeat sends a HEAD /manifest.json request every 30 seconds; a failed heartbeat flips an __effectiveOnline flag that gates the offline banner and triggers queue flushes.

3.5.7 Security Considerations

No trusted client input. User IDs and roles come only from the verified Firebase ID token. Product IDs, quantities, and totals sent from the client are treated as untrusted and re-validated on the server where applicable.

Firestore security rules — All collections require request.auth != null. Write operations are restricted to authenticated users. Admin-only collections (e.g., user profile mutations) require a matching profile role.

Service account isolation — The Firebase Admin SDK credentials exist only as a Vercel environment variable. They are never serialized to the client, never logged, and never included in error responses.

HTML escaping on render. Every dynamic string rendered into innerHTML — customer names, product names, order IDs, error messages, audit log descriptions — passes through an escapeHtml() helper. This prevents stored-XSS through Firestore data.

AI provider isolation. The LLM providers receive only aggregate store snapshots, never raw Firestore documents, user emails, or ID tokens. The prompt explicitly forbids inventing numbers.

3.5.9 Testing Approach

Testing was performed through three complementary mechanisms:

Manual QA — Each feature was exercised end-to-end on Chrome desktop, Chrome Android, and Safari iOS, with particular attention to variant-selection edge cases, offline-to-online transitions, and role-based visibility.

In-browser diagnostics — A __posDiag toolkit and a __posAudit full feature audit were built and run against the deployed system. These enumerate function availability, DOM element presence, Firestore read/write success, backend endpoint reachability, chart instance health, and localStorage integrity.

Production monitoring — Vercel runtime logs capture every API request with status code and error message. Firebase Console provides Firestore quota, latency, and error dashboards.

3.5.10 Known Limitations

The following constraints are documented for future improvement:

  1. Firestore free-tier daily quota — The system was designed around the Firebase Spark (free) plan's 50,000 read/day ceiling. Heavy concurrent usage can exhaust this limit, causing 503 responses. Upgrading to Blaze removes the ceiling at negligible cost for typical store volumes.
  2. Cold-start latency — Vercel Python functions incur a 1–3 second cold-start penalty on the first request after a period of inactivity. Subsequent requests in the same container are fast.
  3. Client-side admin limits — The two-admin maximum is enforced in the UI. A determined user could bypass it via the Firebase Console. This is acceptable for a single-tenant deployment but would need a Cloud Function for multi-tenant use.
  4. Password reset for admin-created accounts — When an admin creates a user, the user's Firebase Auth account is created with the admin's chosen password. The new user is not forced to change it on first login. This is a deliberate simplification; enabling "force password change on next login" would require an additional Cloud Function.
  5. No server-side rendering — The entire UI is client-rendered. This is optimal for an authenticated POS terminal but would need reconsideration if a public storefront were added.
